可以把当前流程理解成：

```text
上传三视图
  ↓
图片预处理
  ↓
可选：GPT 识别家具属性
  ↓
InstantMesh 重建任务
  ↓
加载预训练权重
  ↓
Zero123++ 补全多视图
  ↓
InstantMesh 推理生成三维网格
  ↓
导出 GLB
  ↓
浏览器加载预览
  ↓
用户确认尺寸、属性和朝向
  ↓
保存到家具库
```

### 1. 上传和预处理

前端要求按顺序上传：

1. 正面图
2. 右侧图
3. 顶面图

后端会把图片统一转换成 JPG，并处理 EXIF 旋转、尺寸限制和透明背景。

当前实现还会使用 `rembg` 做背景去除。背景越简单，最终网格越干净；如果旁边有背包、桌子、墙上杂物，模型可能把这些物体一起重建进去。

### 2. 可选的属性识别

如果用户同意，图片会发送到配置的第三方视觉服务，识别：

- 家具类别
- 名称
- 材质
- 颜色
- 宽、深、高
- 扶手、抽屉、支腿等属性

这一步只负责填写家具属性，不负责生成三维网格。

如果不勾选同意，系统仍然可以在本地完成三维重建，用户手动填写属性即可。

### 3. 创建重建任务

后端创建一个 `reconstruction job`，并在后台执行。页面不会一直阻塞，而是每隔几秒查询任务状态。

这就是截图中看到：

> InstantMesh 正在生成三维网格……

的原因。

### 4. 加载模型权重

这里的“下载权重”不是下载某个家具模型，而是下载 InstantMesh 已经训练好的模型参数。

模型权重可以理解为神经网络经过训练后保存下来的大量数字参数，类似模型的“经验”。主要包括：

- Zero123++ 权重
- InstantMesh 重建权重
- DINO-ViT 图像编码器权重

第一次运行时，如果本机没有这些文件，程序会从 Hugging Face 下载。下载后会缓存到本地，例如：

```text
InstantMesh/ckpts
```

之后一般不需要重新联网下载。但是当前实现每次重建都会启动一个新的 Python 进程，因此即使不重新下载，也会重新把模型权重加载到内存和显存，这仍然会花时间。

### 5. Zero123++ 生成补充视角

当前使用的 InstantMesh 原始模型主要是按照多视图输入设计的。

即使用户提供了正面、右侧、顶面三张照片，当前代码仍然会：

1. 用正面图运行 Zero123++
2. 生成一组补充视角
3. 用用户真实的右侧图和顶面图替换部分生成视角

这样可以让 InstantMesh 得到较完整的多视图输入，但 Zero123++ 本身需要运行 diffusion（扩散推理），是当前流程中比较耗时的一步。

### 6. InstantMesh inference（推理）

Inference（推理）就是：

> 使用已经训练好的模型，根据输入图片计算输出结果。

当前阶段不会训练模型，也不会修改权重。GPU 只负责：

- 图像编码
- 多视图特征计算
- 三维特征表示生成
- 网格提取
- 顶点颜色计算

可以这样区分：

| 阶段 | 是否修改模型参数 | 是否需要大量数据 | 当前是否执行 |
|---|---:|---:|---:|
| Training（训练） | 是 | 是 | 否 |
| Fine-tuning（微调） | 是 | 是 | 否 |
| Inference（推理） | 否 | 否 | 是 |

### 7. 导出和预览

InstantMesh 输出网格后，后端将它导出为 GLB 文件，保存到：

```text
runtime/uploads/assets
```

浏览器再加载这个 GLB：

- 如果还没有 GLB，显示模板预览；
- 如果 GLB 已生成但还没加载完成，按钮继续禁用；
- 如果 GLB 已生成并成功加载，才允许“确认并保存到家具库”。

所以截图里的按钮不可用，确实主要是因为当时真实网格还没有生成或还没有载入完成。模板预览不能直接发布成家具库模型。
