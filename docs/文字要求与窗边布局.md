# 文字要求与窗边布局

2026-10-20，针对“桌子靠窗，椅子面朝窗户方向”没有落实的问题修正。

## 问题原因

原来的离线解析器不支持“面朝窗户”。按整句原子处理的规则，第二句不能识别时，第一句“桌子靠窗”也不会写入场景。界面没有持续突出这次失败，用户仍能生成旧条件下的候选，容易误以为新要求已经生效。此前的“靠窗”也只是中心距离软评分；占地不碰撞不等于窗边位置、桌椅关系或朝向正确。

修复前实际响应保存在 [原句复现](../artifacts/interaction_checks/window_request_before.json)：`action=unsupported`，没有返回修改后的场景。

## 现在如何处理

1. 将原句识别为两项绑定明确窗户的要求：桌子靠窗、椅子面朝窗户。直接提出的要求必须满足；带“尽量、最好、优先”的条件参与权衡，不保证满足。旧数据保留软偏好的含义。
2. 在界面显示“已识别的布局要求”。若有多个桌子、椅子或窗户而无法确定目标，会先要求说明；没有窗户或相关家具已锁定时，也不会偷偷修改或忽略。
3. 窗边桌椅先作为一组搜索。桌子靠窗，椅子在桌前并朝向窗户。优先保持未提及家具原位；需要调整未锁定的挡路家具时，在候选摘要中列出。身份、尺寸和锁定位置始终保持。
4. 每个候选分别检查占地和文字要求。没找到同时满足的候选就说明原因，不用“几何检查通过”掩盖要求失败。预览显示距离和角度，蓝色箭头表示椅子正面方向。
5. 指令未识别或有歧义时清除旧候选，明确提示“本次文字要求未应用”。修改重发，或明确点击“忽略本次要求”后，才能按原来已识别条件生成。

明确窗边要求在混合模式中采用局部约束搜索，界面与返回值会说明本次未运行布局网络。原网络没有学习门窗指令，不为了使用模型而先扰乱整屋位置。纯模型模式仍只运行模型，不能满足要求时没有候选。

## 核验规则与边界

当前窗边默认值是产品工程选择：家具占地到真实窗户线段的距离不超过 0.60 米，沿窗方向的投影间隙不超过 0.15 米；椅子正面与目标窗中心方向夹角不超过 20°。它们不来自建筑或人体工学标准，不代表真实采光、视线无遮挡、可开窗、桌椅高度合适或柜门开启合规。

朝向按本系统示意模型的局部 +z 正面计算；导入的外部家具模型也需要正确的正面方向。椅子背靠窗、面朝窗不是同一件事。

## 使用方式

刷新工作台，退出旧候选预览后，直接发送：`桌子靠窗，椅子面朝窗户方向`。先核对“已识别的布局要求”出现两项，再预览候选检查距离、朝向和其他家具移动情况。确认后才应用。

不希望床、书架等被移动时，先在家具清单中锁定它们。如果这使窗前没有足够空间，系统应报告找不到满足条件的候选；不要通过降低验收标准把这种情况称为成功。
