摘要
Roomwise 是一个本地运行的房间家具布局助手，面向搬家、租住和旧家具再利用场景。它把房间、门窗、家具尺寸、保留状态和锁定状态结构化，使用规则搜索、可选的自研布局恢复模型以及独立几何验收，生成可预览、可撤销、可应用的摆放方案。系统支持普通家具相对位置和朝向要求、靠墙/靠窗要求、柜门使用净空，以及收纳箱在桌面或低柜顶部的吸附与承托传播。
本项目的 AI+ 开源融合方式是：以公开研究方法和受限数据作为可复现实验基础，自主编写轻量 set Transformer、中文指令执行器、几何约束搜索、候选验收和前后端应用；模型只负责受控的家具位置/方向恢复，最终结果必须通过独立规则检查。测试集 682 个房间、498 户的中等位置扰动实验中，模型三步恢复的中心位置误差为 0.229 米，未处理为 0.564 米。12 个自制应用场景中，规则搜索与模型加几何修复均通过 10 个普通场景并正确拒绝 2 个明确失败场景。
关键词：家具布局；空间约束；set Transformer；开源数据；可验证 AI；本地应用

1	作品概述
1.1	背景问题
现有家具布局工具通常要求用户手动拖动，或只根据二维坐标和软性评分给出结果。搬家或复用旧家具时，用户关心的是更具体的约束：床应在衣柜左侧或前方，床头柜不能挡住柜门，桌椅需要同时靠窗且相互配合，收纳箱应能放在桌面上并在拖动时保持承托关系。只看中心点距离容易出现家具碰撞、柜门被挡、入口不可达和方案之间只是轻微抖动等问题。
Roomwise 的目标不是替代设计师，也不是从照片直接重建房屋，而是提供一个小而可核验的闭环：用户输入真实尺寸和保留意图，系统提出有限候选，程序逐个验收，用户预览后决定是否应用。

1.2	目标、方向与作品形态
作品形态为本地 Web 应用，后端使用 FastAPI，前端使用 React/Vite/Three.js，本地 SQLite 保存场景版本。参赛方向定位为“AI+ 开源应用创新”：公开可复用的应用代码、约束评价、测试、自制场景和运行说明；受限数据、上游源布局、真实用户照片/视频和衍生权重不随公共代码包再分发。

1.3	核心亮点
1.	模型与规则分工明确。自研模型提供候选恢复，碰撞、越界、门口、柜门净空、通路近似和用户明确要求由独立程序检查。
2.	关系按家具自身朝向解释。普通家具的前后左右随参照家具旋转；床的前后按床头/床尾，左右按站在床尾看床头判断，避免镜头角度改变语义。
3.	支持真实操作闭环。候选先预览后应用；拖动、旋转、锁定、撤销、JSON 导入导出、SQLite 保存和自有家具库形成可回退流程。
4.	候选之间有结构差异。生成器会搜索超过展示数量的方案，并按家具间关系、朝向、靠墙和角落锚点去重；相同关系的坐标抖动不能补足方案数。
5.	开源边界可追溯。代码、版本、实验指标、许可和未完成项分开记录，避免把第三方数据、模型或外部语言接口误称为自主成果。

3	AI 技术、开源及第三方资源选择
3.1	AI 在系统中的作用
AI 作用被限制在三个可验证环节：
1.	布局恢复模型根据家具类别、尺寸、位置、方向、锁定状态和房间边界采样，预测未锁定家具的位置/方向修正量；
 
2.	可选语言模型把自然语言转换为有限的结构化意图，随后由本地 schema、ID、锁定和几何执行器再次检查；
3.	可选视觉/视频入口生成待确认候选，类别、尺寸、数量和位置仍由用户确认，不能把视觉识别当作测量结果。
规则搜索、相对位置摆放、柜门净空、承托箱子、候选去重和验收器均为本次自主实现。

图片建立家具模型属于独立的资产输入环节。这里的目标是生成一个外观和基本轮廓相对接近的可摆放模型，而不是根据图片直接得到测量级的 CAD（Computer-Aided Design，计算机辅助设计）模型。推荐输入一件家具的正面、侧面、背面等多视图图片；如果只有单张图片，也可以先生成草稿，但应把遮挡面、背面结构和真实尺寸标记为待确认。需要注意的是，当前开源模型的常用推理入口仍以单图为主，三视图不能直接视为已经完成了多视图融合；系统应先做视图对齐、主体一致性检查和主视图选择，后续再逐步接入真正的多视图重建流程。

当前调研中，首选路线是 `TRELLIS.2` 的 image-to-3D 推理流程。它以图片生成带纹理的三维资产，支持较复杂的拓扑和 PBR（Physically Based Rendering，基于物理的渲染）材质，代码和模型按 MIT 许可发布。它的官方仓库说明目前主要在 Linux、NVIDIA GPU 环境中验证，至少需要 24 GB 显存，因此更适合作为独立的 GPU 推理服务，而不是直接塞进本地轻量后端。备选路线是 `Hunyuan3D-2.1`，它提供形状生成和 PBR 纹理生成两个阶段，形状、纹理、联合运行大约需要 10 GB、21 GB 和 29 GB 显存。该项目采用 Tencent Hunyuan 3D Community License，存在地域、用户规模和分发条件，正式使用前必须按目标部署地区和发布方式复核，不能简单当作 MIT/Apache-2.0 依赖。

`InstantMesh` 可以作为资源不足时的 Apache-2.0 原型方案。它适合从单张图片生成网格，也支持稀疏视图研究，但对三视图家具的多视图一致性、真实尺寸和被遮挡面仍需要额外处理。因此，本项目不把任一生成模型的输出直接写入家具库，而是统一进入“草稿—预览—尺寸确认—发布”流程。生成结果先转换为 GLB（GL Transmission Format Binary，二进制 glTF）或 glTF，经过网格完整性、朝向、尺寸、纹理和文件大小检查，再保存为家具资产。

3.3	自主开发、融合方式与实质改进
自主实现包括场景 schema、中文离线解析、意图验证、相对位置局部坐标、床头关系、规则模板、门口/柜门/通路近似、承托箱子、候选结构签名、前端预览和测试。开源方法提供可学习的布局恢复思路，工程层将其限制为“建议器”，并增加三道保护：输入身份/尺寸保护、候选独立验收、预览后显式应用。与只输出一个分数或一个模型坐标相比，系统的实质改进是把空间关系和安全边界变成可执行检查，把失败原因和未满足条件返回给用户。

4	设计与实现过程
4.1	功能流程
用户先输入或导入场景，选择家具并确认尺寸、保留和锁定状态；发送文字后，解析器生成结构化偏好，页面展示“已识别的布局要求”。点击“生成布局”后，系统运行规则/模型路径，候选通过验收后进
 
入结构多样性选择。用户可预览方案；主画面只显示方案编号和操作按钮，详细要求检查通过“查看”进入。应用方案才会写回当前场景。

4.2	关键技术实现
模型。 网络为 2 层 set Transformer，隐藏维度 64、4 个注意力头、73,604 参数；输入包括家具类别、尺寸、位置、方向的正余弦、锁定状态和 12 个房间边界采样点。网络无家具顺序编码，输出对家具顺序置换保持一致。训练加入 0.1/0.3/0.6/1.0 米位置噪声、8/20/40/65° 角度噪声和随机锁定，损失为位置平方误差加 0.4 倍方向误差。

关系与几何。 普通家具相对位置使用参照家具旋转后的局部轴；床的正方向按床头端解释。关系验收同时检查间距 0.025–1.50 米和横向投影重叠。柜门默认保留正面 0.70 米使用区及两侧 0.05 米余量。箱子仅
可吸附到规定的平整台面，台面高度不超过 1.50 米、箱高不超过 0.60 米，箱体需完整位于旋转后的台面
内并留 0.03 米边距。

候选生成与多样性。 先搜索多于展示数量的合格候选，再计算家具外轮廓之间的方位、间距、重叠、朝向和靠墙/角落锚点。相同结构签名的轻微坐标抖动不占满候选池；承托箱子恢复后再次进行最终签名筛选。若差异足够的方案不足，系统返回实际数量并说明原因。

安全执行。 所有模型或语言模型输出都要经过 schema、家具 ID 集合、尺寸、锁定状态和几何验收。用户可退出预览，当前场景在应用前保持不变。

图片到家具模型。 图片处理采用异步任务，不阻塞布局页面。任务输入保存原图引用、视图顺序、用户填写的真实长宽高和授权确认；模型只负责生成几何与材质草稿。流程分为五步：先对图片做主体分割、方向统一和背景检查；再用 `TRELLIS.2` 生成带纹理网格，资源受限时切换到 `Hunyuan3D-2.1` 或 `InstantMesh`；随后把网格的底面和竖直方向统一到 Roomwise 坐标系；最后按用户确认的长、宽、高做非等比风险检查和尺寸校准，并导出 GLB。家具实例引用发布后的资产版本，同时保存确认时的类别、尺寸、朝向和缩略图快照，避免后续修改家具库后改变已经保存的房间。

这里要把“看起来像”与“尺寸正确”分开验收。视觉检查关注轮廓、材质、颜色和主要结构；几何检查关注网格是否可加载、是否有明显破面、是否落地、尺寸是否与用户确认值一致。若图片中没有尺度参照，系统不能把模型自身推断的尺寸当作真实尺寸，只能显示为待确认。对柜门、抽屉、椅腿等细部，也不承诺自动恢复可运动部件；布局阶段默认把家具视为一个带尺寸和朝向的整体。

为了保持本项目的可验证边界，图片建模结果发布前必须经过用户确认。确认前只能作为临时草稿预览，不能参加自动布局；确认后才写入家具库并允许添加到场景。当前报告中的布局实验不包含真实图片到三维模型的准确率，因此不能使用现有位置恢复误差替代该项评估。后续应使用获得授权的家具图片，分别统计类别识别、长宽高误差、朝向正确率、网格可用率和人工接受率，并按单图、多视图、遮挡和复杂结构分组报告。

4.3	生成式 AI 辅助开发与团队审核
项目开发、调研、测试分析和本报告初稿使用了生成式 AI 辅助。团队负责需求取舍、代码审阅、许可证核对、运行验证、失败复现和最终文字修改；模型生成内容没有直接视为事实或原创权利。真实语言接口只进行 3 次工程性调用，后续回归使用离线/禁用提供方的隔离环境。

6	创新性与开放价值
6.1	创新点
第一，项目把“家具关系语言”转成参照家具局部坐标，并将柜门净空、床头关系和箱子承托纳入同一验收闭环；第二，项目把模型建议与规则验收解耦，允许模型失败而不牺牲用户场景安全；第三，候选选择从坐标去重升级为关系、朝向和锚点差异，避免多个预览方案只是抖动；第四，应用、测试、数据边界和授权义务一并公开，便于复现和审查。
 
6.2	与常见方案的差异
只用模型输出坐标的方案容易把越界、碰撞或锁定遗漏传给用户；只用规则网格的方案表达能力有限，难以利用训练数据中的布局先验。本项目采用“模型提出、约束筛选、用户确认”的组合，使模型可以承担恢复建议，程序承担不可妥协的硬约束，用户承担最终应用决策。

6.3	社区与维护计划
当前公开仓库包含代码、测试和运行说明，问题可通过 GitHub Issue 反馈，变更通过提交记录追踪。后续计划是增加更多家具类型和可验证的开门/通路模型，补充真实但经授权的用户测试，建立人工偏好评价，并在确认数据授权后再决定是否公开训练产物。不会把受限数据或真实素材直接上传公共仓库。

8	总结与展望
本项目完成了从场景录入、中文约束、AI 候选、独立验收、结构多样性、预览应用到本地保存的闭环。其主要贡献不是宣称一个通用室内设计模型，而是展示如何把开源方法、自研轻量模型、可解释规则和前端交互组合成可验证的 AI 应用。实验显示模型在受控位置恢复上有帮助，但原始输出仍不安全；12个自制场景和 514 项后端测试证明工程链路可运行，不能替代真实用户研究。
下一阶段将优先完成四件事：一是取得并记录数据、权重和展示素材的最终授权；二是完成图片到 GLB 家具资产的草稿、尺寸确认和版本发布流程；三是邀请用户进行有任务、有时间和偏好指标的对照测试；四是完善开门轨迹、通路、无障碍和更多房型的几何模型。商业化不是本阶段目标，若未来探索，也应建立在授权、隐私和安全验证完成之后。
