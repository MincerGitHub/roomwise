# Roomwise implementation contract

Project: local, single-room furniture placement prototype. Backend package `backend/roomwise`, frontend `frontend`. Runtime binds 127.0.0.1. Units metres, ground axes x/z, height y. Item rotation in degrees around y; positive 90 swaps width/depth. Scene polygon coordinates in same frame as items; rectangular default [0,0]→[width,depth]. No item identity/size changes during generation.

Scene JSON:

Items additionally support optional `y` (base elevation in metres, default 0) and `supportId` (the flat-top host item ID). Defaults are omitted on serialization for compatibility with existing scenes. `storage_box` extends the catalogue to 21 categories. Only storage boxes up to 0.60 m high can attach; eligible hosts are `desk`, `table`, `coffee_table`, `nightstand`, `tv_stand`, `cabinet`, `children_cabinet`, on the floor and at most 1.50 m high. Every rotated box corner must remain 0.03 m inside the host footprint, and `y` must equal the host's height. Missing, cyclic, overhanging, unsupported and floating attachments fail geometry validation. Collision checks use vertical intervals as well as footprints; ceiling checks include base elevation. No mass/load capacity is inferred.

Manual dragging uses a 0.16 m entry distance from the nearest fully supported pose, with 0.25 m retention to reduce edge flicker. A box remains movable on the surface and detaches to y=0 beyond that distance. Other objects at the same elevation block snapping. Host transformations carry attached boxes; locked boxes prevent moving or removing their hosts. Generation searches floor furniture and carries each attachment with its host, then independently validates the complete scene and original preferences. Persisted `supportId`/`y` survive preview, undo, JSON transfer and scene storage. These fields describe a single support layer; boxes, seating, beds, mirrors and open shelving are not hosts.

```json
{"id":"demo","name":"搬家后的卧室","version":0,"room":{"width":5.2,"depth":4.2,"height":2.7,"polygon":null,"door":{"wall":"south","offset":0.45,"width":0.9,"clearance":0.9},"windows":[{"id":"window-1","wall":"north","offset":2.3,"width":1.5,"sillHeight":0.9}]},"items":[{"id":"bed-1","label":"旧双人床","category":"double_bed","width":1.8,"depth":2.0,"height":0.55,"x":2.5,"z":2.1,"rotation":0,"locked":false,"keep":true,"source":"brought","assetUrl":null,"photoUrl":null}],"preferences":[]}
```
All 19 bedroom classes supported: armchair,bookshelf,cabinet,chair,children_cabinet,coffee_table,desk,double_bed,dressing_chair,dressing_table,kids_bed,nightstand,shelf,single_bed,sofa,stool,table,tv_stand,wardrobe. Add rug as non-solid exception. Source brought|existing|new. `assetUrl` and `photoUrl` optional. Preferences `{kind:'near_window',itemId:'desk-1'}` or `{kind:'min_move',itemId:'bed-1'}`.

Window requests also support `{kind:'face_window',itemId:'chair-1',targetId:'window-1',required:true}`. Old preferences default to `required:false`. Explicit Chinese requests without 尽量/最好/优先 set `required:true`; vague targets with multiple windows require clarification. Furniture forward is local **+z**, mapped by yaw to `(sin(rotation), cos(rotation))` in the floor plane. This matches the procedural chair mesh; imported assets must use the same forward convention.

`window_constraints.evaluate_layout_requirements(scene)` independently checks near-window footprints and facing directions. Current product defaults: footprint-to-window-segment distance <=0.60 m, along-window projection gap <=0.15 m, and forward-to-window-centre angle <=20°. These are configurable engineering defaults, not building, lighting or ergonomic standards. `validate_scene` remains a geometry check; `/validate` additionally returns `requirements:{satisfied,checks,unsatisfied,thresholds,note}`. Generation accepts a candidate only if geometry is valid AND every required condition is satisfied. Soft conditions may remain unmet, with explicit feedback.

Cabinet door use zones are hard geometry constraints in validation and generation. Wardrobes, cabinets, children cabinets and TV stands reserve 0.70 m in front of their confirmed facing direction, with 0.05 m lateral margin. Supported custom furniture with confirmed `doorCount > 0` uses the same zone; confirmed `doorCount = 0` disables the default. Other solid furniture occupying the zone returns a `cabinet_door_clearance` error and rejects the candidate. Rugs are treated as floor layers. This is an engineering use-area default, not an exact hinged-door sweep or building-code check.

Cabinet door use zones are hard geometry constraints in both `/validate` and generation. Wardrobes, cabinets, children cabinets and TV stands reserve 0.70 m in front of their confirmed facing direction, with 0.05 m lateral margin. Supported custom furniture with confirmed `doorCount > 0` uses the same rule; confirmed `doorCount = 0` disables the default. Other solid furniture entering the zone returns a `cabinet_door_clearance` error and rejects a generated candidate. This is an engineering use-area default, not an exact hinged-door sweep or building-code check.

For explicit window requests, rules/hybrid generation uses local desk/chair grouping on the user's original scene. It first keeps unrelated furniture in place, then repositions only unlocked blockers when possible. Hybrid labels these results `mode:'rules'`, `provenance.layoutNetwork:false`, `constraintSearch:true`; it does not pretend the whole-room denoiser understood window instructions. All additional movements are listed in candidate changes/summary. Failed or ambiguous commands are atomic: no partial edits, no silently reusing old candidates.

`near_wall` preferences may specify `wall:'nearest'|'north'|'south'|'west'|'east'` and `required`. Required spatial requests use the local constraint path and bypass ordinary whole-room templates. For ordinary `rules`/`hybrid` proposals, `layout_templates.functional_template` first attempts functional groups: bed head at a wall, nightstands at the bed's head sides, chair facing its table, and storage backs toward walls. Original identity, dimensions and locked transforms remain invariant; template failure falls back to other bounded searches. Template candidates report `provenance.initialization:'functional_group_template'`, `functionalGroups:true`, `layoutNetwork:false`, `geometricRepair:false`; do not describe them as trained-network outputs or verified ergonomic design.

`relative_position` preferences use `{kind:'relative_position',itemId:'bed-1',targetId:'wardrobe-1',direction:'front'|'back'|'left'|'right',required:true}`. Both IDs must identify different existing solid items. One relative target per subject is supported; targets cannot also be relative subjects (no chains). The target retains its original position, rotation and lock state throughout rules/hybrid/model generation. Directions use its rotated local axes: ordinary front is +z; ordinary left/right are the viewer's sides while standing in front and facing the furniture front; bed front/back are the head/foot ends and bed left/right retain the bedside convention. A furniture snapshot's `frontDirection:'negative_z'` reverses ordinary front/back. Gap between projected footprints must be 0.025–1.50 m with lateral overlap at least `min(0.12 m, 25% of the narrower footprint span)`. The requirement checker returns `direction`, `gapMeters`, `lateralOverlapMeters` and corresponding thresholds. These are product defaults. Required relations gate candidate acceptance alongside all existing spatial and geometry checks; soft relations participate in search and scoring with unmet checks shown. Simple Chinese directions run locally even when a language provider is configured. Validated language plans also support `relative_position`, retain `required:false`, and compile into the same executor. Bedside and vanity seating keep their specialized constraints. Negative or partially recognized relative commands do not execute. All generated layouts remain previews until applied.

`face_item` preferences use `{kind:'face_item',itemId:'chair-1',targetId:'table-1',required:true}`. The subject's declared front (`+z` for ordinary furniture, `-z` for beds or snapshots with `frontDirection:'negative_z'`) must point toward the target centre within 20°. Placement stages an unlocked target first, then fixes its chosen candidate pose while searching for a clear subject pose. A locked target remains at its input pose. The request is checked together with collision, door, cabinet-door clearance and accessibility rules; generated candidates that cannot satisfy it are rejected.

API (frontend prefix /api proxied to localhost:8765):
- GET /health -> {status,modelLoaded,videoDetector,...}
- GET /catalog -> {items:[{category,label,width,depth,height,...}]}
- GET /demo -> Scene
- POST /validate {scene} -> {valid,issues:[{type,severity,message,itemIds}],metrics:{collisions,outOfBounds,doorConflicts,reachable,checkedItems,...}}
- POST /generate {scene,mode:'hybrid'|'rules'|'model',count:3,seed:42} -> {baseVersion:scene.version,candidates:[{id,scene,validation,score,mode,summary}],diagnostics:{...}}. Return failure explicitly if no accepted candidates. Original locked transforms and ALL identity/size/keep/source protected.
- POST /command {scene,text,selectedId?} -> {baseVersion,action:'edit'|'generate'|'suggest'|'undo'|'clarify'|'unsupported',scene?,message,changes?:[],suggestions?:[],needsConfirmation?:bool,interpretation?,language?}. Optional `intent_planner` uses a configured provider to translate text into a limited validated plan; the deterministic parser remains available offline. Commands can return generate intent, caller invokes generate with updated preferences/locks. Explicit relative moves/rotations combined with `only_adjust` return `edit` without automatically generating again. Existing locks cannot be implicitly overridden.
- POST /suggest {scene,need:'work'|'storage'|'reading'} -> {suggestions:[{category,label,width,depth,height,reason,...}]}. User must accept.
- POST /scenes/save {scene} -> {id,version}; GET /scenes -> {scenes:[...]}; GET /scenes/{id} -> Scene. Server optimistic version rejection where saved state exists. Caller can use import/export JSON with same fields.
- POST /assets multipart file -> {url,name,type}; local glb/gltf or image accepted safe filename. No arbitrary path.
- POST /video/analyze multipart file -> {jobId}; GET /video/jobs/{jobId} -> {status:'queued'|'processing'|'complete'|'failed',progress,frames:[{id,url,timestamp,sharpness}],candidates:[{trackId,label,category,confidence,frameUrl,bbox}],detector,limitations,error?}. Candidate category is provisional; requires human confirmation, no inferred dimensions.
- GET /experiments -> summary of real available model experiment artifacts, absent -> honest no results.

Model module `roomwise.learning`: `model_status()` and `refine_scene(scene:dict,iterations:int=3)->dict`. Model absent must report unavailable, never fabricate model generation. Root owns venv dependency installation. Agents do not edit each others' files; backend geometry tests validate ML output independently.

Language boundary (2026-10-20): current local application is configured for optional DeepSeek `chatcompletions`/`json_object`. Only the current instruction, selected ID and allowlisted room/item geometry, labels, locks and preferences leave the backend; photographs, reference images, asset URLs, meshes and local paths are excluded. Requests may incur provider charges. The local config is private, reloaded per command, and overridden by `ROOMWISE_LANGUAGE_PROVIDER=disabled` in isolated regression servers. A schema-valid response is not evidence of correct intent. Supported plans must reference existing objects and capabilities; unsupported or ambiguous whole instructions do not partially execute. `keep` protects identity, whereas phrases such as 保持原位 require `lock`; missing or contradictory position locks reject the whole plan and request restatement.

Three real DeepSeek responses are preserved in `artifacts/interaction_checks/deepseek_live_commands.json`: a correct bookshelf/wall plan, an omitted wardrobe lock (`keep` instead), and correct relative movement with the old erroneous `generate` dispatch. Guards and dispatch were corrected after observing them; no fourth paid call validated the fixes. Do not report 3/3 intent accuracy or majority-command coverage. Automated checks must use provider `disabled` on backend8766 and `frontend/vite.integration.config.ts` proxying to8766; production8765 may have a live paid configuration. Mock transport checks do not measure the external model or visual design quality.

Ownership: backend agent schemas/geometry/generator/commands/storage/API/tests. Model agent learning.py + scripts + artifacts + training/evaluation tests. Video agent video.py + setup model downloader + video tests. Root frontend/integration/docs/launcher. No public publish, no redistributing restricted training arrays. Use self-made procedural furniture meshes in demo.
# 自有家具图片输入（2026-10-23）

- `GET /api/furniture/status` -> `{enabled,provider,model,reasoningEffort,message}`，不返回密钥或完整服务地址，message 明示第三方接收域名。视觉服务独立于语言服务，默认 `ROOMWISE_VISION_PROVIDER=disabled`。启用仅允许 `openai`（大小写不敏感）、用户指定的根地址 `https://api.tokenlab.pro`、型号 `gpt-6-sol` 和推理强度 `high`；配置其他值不外发。provider 仅表示协议类型，不能证明网关为 OpenAI 官方或验证上游模型身份。enabled 仅表示本地配置合规，不证明账户权限或网关兼容性。
- `POST /api/furniture/analyze`：multipart `files`（1—3 张 JPEG/PNG/WebP，每张最多 10 MB、4000 万像素）及 `consent=true` -> `{draftId,jobId}`。不要求客户端先选类别。后端校正方向、移除元数据，原尺寸重编码副本留本地，缩放副本联合发送用户指定的第三方 `https://api.tokenlab.pro/responses`，使用 Bearer 鉴权、`model=gpt-6-sol`、`reasoning.effort=high`、严格 JSON Schema 及本地 Pydantic 校验，`store=false`。模型目录 `/v1/models` 不作为推理地址；不自动尝试 `/v1/responses` 或其他端点。连接超时 15 秒、读写超时 180 秒。拒绝、截断、限流、模型不可用均保留草稿，不自动重试或降级。用量字段为 `input_tokens`、`output_tokens`、`total_tokens`。
- `GET /api/furniture/jobs/{jobId}` -> `{id,draftId,status:'queued'|'processing'|'complete'|'failed',error,errorCode,result?,metrics?,updatedAt}`。SQLite 持久化，单工作线程，无自动付费重试。重启后的未完成任务标为 `failed/interrupted`；只支持单后端工作进程。
- `GET /api/furniture` -> `{assets,drafts}`，仅列出未发布草稿及各资产最新版本；`GET /api/furniture/{assetId}` 读取当前资产，`GET /api/furniture/drafts/{draftId}` 读取草稿。
- `POST /api/furniture/drafts/{draftId}/save`：`{expectedVersion,properties}` -> 更新后的草稿。运行中、已发布或旧版本拒绝修改。`properties` 包含名称、受支持类别或 null、细分类别、宽深高或 null、尺寸来源/依据、受约束结构参数、风格与规范方向；尺寸变化由后端标记为 `user`。
- `POST /api/furniture/drafts/{draftId}/retry`：`{consent:true}` -> `{draftId,jobId}`。明确重试才可重复调用，运行中重复请求返回 409；已发布家具修订不重发旧照片。
- `POST /api/furniture/drafts/{draftId}/publish`：`{requestId,expectedVersion,assetUrl,confirmations:{category:true,label:true,dimensions:true,direction:true,structure:true}}` -> 已确认资产。`assetUrl` 必须指向已上传到本机的 GLB；缺字段、未确认、目标混淆或视图冲突不能发布。`requestId` 持久去重，同一草稿重放返回同一资产及版本，不重复发布。
- `POST /api/furniture/{assetId}/edit`：`{}` -> 修订草稿。发布时资产版本递增并检查基础版本，旧场景不联动更新。
- 场景 `Item` 增加可选 `furnitureAssetId`、`furnitureSnapshot`；未使用的新字段不输出，旧场景不要求迁移。引用家具资产的实例必须携带 `dimensionsConfirmed:true` 的完整快照：资产版本、确认时名称/类别/尺寸、颜色/结构参数、尺寸来源、照片及方向等。实例独立复制，保存、布局与命令处理保留快照；旧快照不依赖家具库在线可查。照片主图和 GLB 继续使用 `photoUrl`、`assetUrl`。
- 参数化预览、场景程序化回退和 GLB 导出共用构造器，近似模型规范化为确认的宽深高、中心与地面；床头为局部 `-z`，其他家具使用面为 `+z`。布局仍按矩形占地而非网格碰撞。未识别结构用模板补全，材质/风格不是物理认证。
- `ROOMWISE_RUNTIME_DIR` 可隔离场景、家具与视频运行文件；默认仍为原本的项目 `runtime`。测试必须关闭视觉及文字服务并使用隔离目录。JSON 导出不包含资源本体，不承诺跨设备可直接显示资产。
- 外发边界：第三方网关请求只包含固定提取提示、字段协议及预处理图片，不含房间、指令历史、图片 URL、本地路径或网格。不读取 Codex 配置或登录凭据，独立后端密钥仅来自 `ROOMWISE_VISION_API_KEY`。现有语言接口白名单不变，不发送新增家具快照。真实模型实测须单独明确启用，不以模拟测试冒充真实准确率。
- 三维拾取的身份只来自场景实例根节点，忽略导入模型内部的 `userData.itemId`；兼容早期含预览标识的 GLB。新导出的家具资产不包含实例标识，避免资产元数据污染场景选择与拖动。
- 视觉配置自动读取应用根目录 `.env.vision`（可用 `ROOMWISE_VISION_ENV_FILE` 指定），仅解析视觉配置白名单；进程环境变量优先，不修改全局环境。非法编码、格式或超大配置文件安全禁用外发，不回显文件内容。`GET /api/health` 增加 `application=roomwise`，供本机启动器辨别端口冲突。

# 床头关系补充（2026-10-20）

`bedside` 偏好的 `itemId` 必须引用床头柜，`targetId` 必须引用真实床，`side` 为 `left`、`right` 或 `either`。床头在床局部 `-z`；站在床尾看床头时，床局部 `+x` 为右侧。生成结果的空间合法性、明确要求和默认家具关系分别验收。可移动床头柜必须满足床头侧关系，不能以软评分替代；锁定柜体保持原位，有问题时明确显示，硬要求冲突不能冒充通过。完整的明确床头柜短句由本地执行器处理，无需模型 API；未支持的复合要求不能只执行一部分。
