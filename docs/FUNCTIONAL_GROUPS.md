# 桌椅功能组与 GPT 指令接入

## 桌椅分配

工作桌包括书桌、餐桌和梳妆台；座椅包括普通椅、扶手椅、梳妆椅和凳子。程序先构造全部类别兼容的桌椅候选边，再用带桌子容量的全局最小代价最大匹配选择实际关系。每把椅子最多归属一张桌子，餐桌允许分配多个座位。

优先采用用户明确指定的家具对象；同一个窗户上的“桌子靠窗”和“椅子面朝窗户”关系次之。剩余分配考虑已声明的台面与座面高度、专用座椅类别及距离。类别是排序因素，普通椅也可以成为梳妆台的候选。明确的相对位置约束会暂停相关椅子的自动配对。茶几仍通过沙发与茶几的独立关系处理。

书桌与梳妆台默认一个座位，餐桌默认四个。可以在场景物品或家具快照的功能参数中声明容量：

```json
{"functionalProfile": {"seatCapacity": 2}}
```

已有家具快照的 `parameters.seatCount` 也可提供容量。容量表示最多分配多少把椅子，不会自动创建、删除家具或缩放尺寸。座位还必须通过空间与功能检查；声明四个座位并不保证任何房间中都能安排四把椅子。未知台面/座面高度保持未知，不用家具总高代替。

布局模板、靠窗约束搜索、功能空间检查、梳妆座椅检查和布局评分共同使用此分配规则。生成过程中按输入场景的配对检查，输出再通过与页面相同的独立验收。碰撞、门口、柜门净空、墙面及窗户约束继续生效。

搜索保留原来的时间和次数上限。没有搜索到候选不证明数学上无解；默认使用空间建议可能仍有提示，已声明的必须条件和必须文字要求不能被候选违反。

## GPT Responses 接口

本地语言配置支持 `provider: "responses"`、服务商 URL、模型名、API 密钥以及可选的 `reasoningEffort`。公开配置模板见 [环境变量示例](../.env.language.example)，具体账户与密钥需要在本机配置。请求使用 JSON schema 输出，保持原有家具引用、锁定和操作白名单校验；仅处理完整的助手文本，不执行工具调用、拒绝结果或未完成的计划。不自动重试，单次 Responses 请求最多等待 120 秒。

完整且明确的基础靠窗、朝向窗户指令由本地规则识别，消息会说明识别方式。带有其他要求的句子不会截取一部分后执行。认证、权限、服务商内容策略、限流、超时、网络和输出格式错误分别给出固定提示；不向页面暴露密钥、地址或远端原始错误。

## 验证

后端回归覆盖完整候选图、全局分配、容量、明确对象关系、多桌多椅、窗口要求、家具尺寸与锁定保留，以及网关错误分类。页面回归覆盖原始冲突场景的生成、预览、应用、保存，及餐桌两把椅子与独立书桌办公椅同时分配。本次发布副本保留 GitHub 已有的常驻预览与界面布局，另行验证合并后的版本。
